# macOS drop-in compatibility contract

**Scope:** ARM64 Darwin executables launched by `arm64-metal` on Apple Silicon. This matrix qualifies named contracts, not macOS generally. A green fixture proves only its artifact, inputs, flags, runtime, and host envelope. There is no aggregate compatibility percentage.

**Snapshot basis:** source baseline `2164127` on `codex/tu-thread`. The worktree already contains separate, uncommitted changes to `component-manifest.json` and `tools/verify-components.py`, plus `fixtures/handoff/exit-status-133.c`; this document does not certify those changes. Do not treat historical results below as verification of baseline `2164127`.

## Reproducible envelope and gates

Record source revision; runtime, metallib, package, fixture, and input SHA-256; executable architecture and SDK/minimum OS; macOS product/build, machine and Metal device; argv, environment, launch flags, cwd; native and guest stdout/stderr/raw returncode/normalized status; side effects; timeout and trace. Keep a separate run receipt for each exact runtime. The recorded `b6e8994` example was Apple M4 Pro, macOS 27.2.1; its hashes are below. `COMPATIBILITY.md` used to describe an older `a44fb9c` / macOS 27.0.1 checkpoint; that header is superseded.

Run focused fixtures first, then integration and unchanged binaries. Current gate map:

## Differential decision order

1. Establish the native positive and assert output, errors, status, side effects, and raw returncode in the fixture itself.
2. Run the matching Metal case with a bounded timeout and frozen runtime; preserve each stream/status and boundary trace separately. A guest negative is meaningful only if its native positive control ran and passed.
3. If a contract fails, localize the first divergent service/instruction from the trace; keep a small reusable fixture before replaying an unchanged binary.
4. Then progress unchanged command-line workloads from small named/stdin input to larger/multi-block and threaded modes. Historical decompression examples are `gzip`, `bzip2`, `xz`, and `lz4`; those receipts are workload-specific, not prerequisites to running the fixture gates.
5. Next test startup/cache/framework clients, then JNI/JVM and GUI independently. Record red, intentional architectural exclusion, and unverified separately; a later pass supersedes only the exact case/runtime it reruns.

## Pointer-signing and parent context

Address-diverse signed pointers are context-sensitive: preserve the guest pointer, key, modifier, and storage/parent address used to sign; do not treat a signed child value as interchangeable with the same raw address or with a token signed for another parent slot. The current runtime models selected authenticated pointers in software (token bucket plus guest address/modifier), not Apple hardware PAC. `LEDGER.md` records specific positive evidence for address-diversified stack probes and signed callbacks, plus selected wrong-key/modifier/unsigned negatives; each remains fixture-scoped. For a new pointer path, compare signed value, authentication result, and failure behavior using the exact parent/storage context on native and Metal.
